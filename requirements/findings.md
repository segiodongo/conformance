# Findings from linking the tests to the catalog (demo)

> **Demo only, not for merge.** These findings come from giving each of the 133
> shopping tests a marker against the catalog at `f2626c28` (see
> [Linking tests to rules](README.md#linking-tests-to-rules)). Rule IDs are the
> demo's stable IDs without the `REQ-SHOPPING-` prefix. They aren't official.

## Summary

- **Markers:** 85 tests cite rules, 24 are `no_rule`, 16 are `scenario`, 6
  are `outside_catalog` and 2 are `older_version`.
- **Rules cited:** 101, all testable: 90 MUST, 8 MUST NOT and 3 SHOULD.
- **Coverage:** the tests cite 98 of the 104 testable MUST and MUST NOT rules
  (94%): catalog 18 of 18, order 17 of 17, cart 8 of 8, discount 4 of 4,
  checkout 35 of 37, fulfillment 13 of 16 and buyer consent 3 of 4.
- **Depth:** all 98 are checked in full (see
  [Claims reviewed](#claims-reviewed)). ORDER-0022 is cited in part by the
  envelope test and in full by the test that verifies the signature value,
  so the coverage report counts 98 of the 104 (94%) as fully checked and
  none only in part.
- **Sample server:** against `samples` at `360adbc`, with the marker check
  on, 81 of the 133 shopping tests pass, 1 fails (Get Order answers an
  unauthenticated request; see [Sample server findings](#sample-server-findings)),
  20 don't apply (the server implements 2026-04-08, which doesn't state the
  rules they cite), 16 skip because the sample doesn't advertise the catalog
  capabilities (14) or the embedded transport on `dev.ucp.shopping` (2), 10
  skip because no trigger is declared, 2 skip as not
  exercised (the sample emits no `options[].description` and omits
  `continue_url` on `incomplete` and `ready_for_complete` checkouts), and
  the 3 TLS tests skip: the sample is reached over `http://` on localhost, so
  there is no TLS to check.

### Rule scope

CHECKOUT-0010 ("A revision MUST be returned as a revised line `quantity` with
an explanatory `messages[]` entry") and CHECKOUT-0011 ("MUST NOT silently
reinterpret the requested quantity") sit in the Ordering increment paragraph.
The next sentence, CHECKOUT-0012, says the business "MAY also revise a
quantity for its own reasons (for example, limited stock)". This review reads
0010 and 0011 as covering those revisions too, which matches the Business
Outcomes example in `checkout/rest.md`: a `quantity_adjusted` warning for
limited stock. Saying so explicitly would remove the doubt.

The tests target the 2026-04-08 release; the catalog is the later draft.

### Rules on pages the catalog doesn't cover

The catalog covers `docs/specification/shopping/` only. Two tests check rules
on `overview/index.md`: service advertisement, and the `version_unsupported`
error for an unsupported version. Two check rules in `signatures.md`: the
components a signature covers, and that a business's profile URL points to
`/.well-known/ucp`.

The components a webhook signature must cover changed with ucp#659 (merged
2026-10-16, after the 2026-08-25 release): `webhook-id` and
`webhook-timestamp` joined the list. The verifier holds a server to the list
its advertised version states, so a 2026-04-08 server isn't failed for
leaving them out, and a draft server is.

### Rules rendered by a macro

The shopping REST pages render their shared header requirements with the
`header_requirements` macro (ucp#819): `UCP-Agent` on every request, and how a
server handles an `Idempotency-Key`. The extractor reads the macro call, not
the text it renders, so the catalog has none of these rules for the checkout,
cart, catalog and order REST pages. The release history found them: the
checkout, cart and catalog REST pages state them in full up to 2026-08-25,
and the lodging pages still do. Expanding the macro before extraction would
add them, and change the counts above.

## Test findings

- **Transport:** every REST binding page states the same two Protocol
  Fundamentals, so each capability has a strict-JSON test and a TLS test.
  The JSON check reads bodies the way RFC 8259 asks a receiver to; Python's
  default parser accepts `NaN` and `Infinity`, so the tests refuse them
  explicitly. The TLS check asks for both halves of "minimum TLS version
  1.3": a 1.3 handshake completes and a 1.2 handshake is refused. Hosts that
  accept TLS 1.2 alongside 1.3, which many CDN defaults do, fail it. If the
  specification means "support 1.3" rather than "refuse older versions",
  the wording should say so; until then the tests hold to the text.
- **Cart suite:** `shopping/cart/cart_test.py` adopts the four assertions of
  conformance PR #108 with the suite's markers and helpers, and tightens
  two: DISCOUNT-0003 requires the code itself on the checkout (a negative
  `discount` total could be an automatic discount), and CART-0025 compares
  the cancel response with Get Cart rather than with the cart as created. It
  adds the buyer as a second overlapping field for CART-0003 and CART-0004.
  Two behaviours it relies on have no rule: that a cart keeps the buyer it
  was created with, and that a valid code applies to a cart; the tests skip
  as not exercised when they don't hold.
- **Accepts what the spec doesn't describe:** the 6 `ValidationTest` tests
  also accept a 4xx for a business outcome. `test_repeated_cancel` accepts a
  200 or an error, so it can't fail on CHECKOUT-0119.
- **Looks only for `discount` entries:** `test_unknown_discount_code`,
  `test_code_matches_case_insensitively`, `test_discount_total_is_negative`
  and `test_empty_codes_removes_discount`. The discount page reports
  line-item discounts as `items_discount`, so a business that allocates
  discounts to line items fails three of them, and passes the fourth without
  a real check.
- **Doesn't check rejection messages:** no test checks the `messages[]` entry
  for a rejected code (`discount_code_invalid`, with the `warning` type that
  DISCOUNT-0005 recommends).
- **Assumes no tax or fees:** `test_fulfillment_flow` expects the total to be
  exactly the price plus the shipping option.
- **Duplicate:** `test_structured_error_messages` sends the same request and
  makes the same assertions as `test_out_of_stock`.
- **Signatures, both ways:** the suite now signs every request it sends
  (RFC 9421, ES256 by default) and publishes the key in the agent profile,
  so a business that verifies platform signatures can authenticate it; and
  it verifies the business's webhook signatures against the keys the
  business profile publishes. The old `test_signature_covers_ucp_agent`,
  which read the component list and skipped on a missing `ucp-agent`, is
  replaced by that verification. `ucp-agent` coverage follows the normative
  table, which required it at 2026-04-08 already; the order page's example
  that omitted it was fixed by ucp#659.
- **Names that don't match:** `test_complete_is_idempotent` checks that a
  second completion is refused.
- **Skips that could hide a failure:** the signature tests used to skip when
  deliveries carried no signature headers at all. Now both fail on an
  unsigned delivery (order.md: payloads MUST be signed).
- **Catalog suite:** `shopping/catalog/lookup_test.py` and

## Sample server findings

`Universal-Commerce-Protocol/samples` at `360adbc`, which passes all but one
of the tests that apply to its version:

- It adds `PUT /orders/{id}` and `POST /testing/simulate-shipping/{id}`,
  which the specification doesn't define.
- It answers business outcomes such as an out-of-stock item with a 4xx (409,

  quantity, so `test_quantity_revision_is_explained` would skip on it even
  if its version stated CHECKOUT-0010 and 0011.
- It signs webhook deliveries with ES256 and covers `ucp-agent`,
  `idempotency-key`, `webhook-id` and `webhook-timestamp`; the signature
  verifies against the key in its `signing_keys[]`.
- It returns order data to a request with no credential at all, which fails
  ORDER-0009 and ORDER-0015 (Get Order MUST authenticate before answering).
  It does require the `Idempotency-Key` and `Request-Id` headers on Get
  Order, which the binding doesn't ask of a GET.

## Coverage gaps

6 testable MUST and MUST NOT rules have no test: checkout 2, fulfillment 3
and buyer consent 1. Catalog (18 of 18), order (17 of 17), cart (8 of 8) and
discount (4 of 4) have all of theirs covered. Each remaining rule is a
candidate for specification clarification or `review.json` reclassification.
